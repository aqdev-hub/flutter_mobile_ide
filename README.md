# Flutter Mobile IDE

بيئة تطوير Flutter مصغّرة تعمل بالكامل على الهاتف: فتح مشروع من الجهاز، شجرة
ملفات كاملة (CRUD + نسخ/قص/لصق)، محرر أكواد احترافي (تلوين نحوي، أرقام أسطر،
auto-indent، auto-close، بحث/استبدال، تبويبات متعددة)، ومعاينة **حيّة وتفاعلية
حقيقية** (وليست صورة أو محاكاة) عبر مُفسِّر Dart مُقيَّد يبني ودجتس Flutter
فعلية.

---

## 1) القرار المعماري وسببه

**المعمارية: Feature-first مع طبقة core مشتركة (Hybrid Layered/Feature)**

```
lib/
├── core/            # ثوابت، ثيم، أدوات مشتركة بلا منطق أعمال خاص بميزة واحدة
├── features/
│   ├── project_explorer/   # شجرة المشروع + نظام الملفات
│   │   ├── data/            # النماذج + FileSystemRepository (dart:io فقط هنا)
│   │   ├── logic/           # Riverpod: ProjectNotifier + ProjectState
│   │   └── view/             # شجرة الملفات + الحوارات
│   ├── editor/               # تبويبات + محرر الكود + بحث/استبدال
│   ├── preview/               # المُفسِّر + محرّك المعاينة + اللوحة
│   ├── console/                 # سجلّ الرسائل المشترك
│   ├── search/                   # بحث عبر ملفات المشروع
│   ├── settings/                   # إعدادات دائمة (ثيم/خط/ترحيب)
│   ├── onboarding/                  # شاشة الترحيب الأولى
│   └── shell/                        # تجميع الواجهة (Activity Bar / Top Bar / Bottom Panel)
├── app_shell.dart      # الشاشة الرئيسية بعد الترحيب (تنسيق فقط، بلا منطق)
└── main.dart
```

**لماذا هذا الاختيار تحديدًا؟**

- كل feature تملك 3 طبقات فقط (`data` / `logic` / `view`) — كافية لتطبيق
  بهذا الحجم دون التعقيد الزائد لـ Clean Architecture الكاملة (usecases/
  entities منفصلة) التي تُبرَّر عادة في تطبيقات أكبر بكثير أو بفرق متعددة.
- **فصل واضح بين UI / state management / نظام الملفات / تنفيذ المعاينة**
  (طلب صريح في المتطلبات): `FileSystemRepository` هو المكان الوحيد الذي
  يلمس `dart:io`؛ `Interpreter` هو المكان الوحيد الذي "ينفّذ" كود المستخدم؛
  الـ providers لا تعرف تفاصيل أيّ منهما، فقط تُنسّق بينها.
  لا شيء آخر في المشروع يستدعي `dart:io` أو يقيّم AST مباشرة — أي تغيير في
  طريقة القراءة/الكتابة أو في محرّك التفسير يبقى معزولًا داخل ملف واحد.
- **Riverpod** (كما اخترت): كل feature لها `StateNotifierProvider` مستقل
  (`projectProvider`, `editorTabsProvider`, `previewProvider`, `consoleProvider`,
  `settingsProvider`, `projectSearchProvider`) بدل provider ضخم واحد — هذا
  يعني أن تعديل حالة الشجرة لا يُعيد بناء المحرر، وتشغيل المعاينة لا يُعيد
  بناء شجرة الملفات، إلخ. الـ providers تتواصل عبر `ref.read` عند الحاجة
  (مثلًا: `ProjectNotifier` يكتب رسائل في `consoleProvider`).
- **قابلية التوسّع**: أي ميزة جديدة (مثل Git، أو Terminal فعلي) تُضاف كمجلد
  `features/<name>/` جديد بنفس النمط دون لمس بقية المشروع.

## 2) خطة التنفيذ (المراحل)

- **Phase 1 (منفَّذة في هذا التسليم):** شجرة الملفات الكاملة + المحرر
  الكامل + التبويبات + الكونسول + البحث + الإعدادات + شاشة الترحيب +
  معاينة حيّة تعمل على **مجموعة جزئية موثَّقة من Dart** (راجع القسم 4).
- **Phase 2 (مقترحة، غير منفّذة):** استبدال المُفسِّر اليدوي بمكتبة
  `dart_eval` لتغطية Dart كاملة تقريبًا (حلقات for/while، دوال مساعدة
  متعددة، مكتبات pub مسموح بها) عبر جسور (bridges) للودجتس المستخدمة هنا
  فعليًا كنقطة بداية.
- **Phase 3 (مقترحة):** فهرسة بحث مسبقة للمشاريع الكبيرة، Git بسيط،
  Terminal حقيقي عبر `flutter_pty`/عمليات محلية إن كانت الصلاحيات متاحة.

---

## 3) لماذا لا يوجد "تشغيل Flutter حقيقي" (Hot Reload فعلي لمشروع كامل)؟

هذا أهم افتراض في كامل التصميم، ويجب توضيحه بصراحة:

تشغيل مشروع Flutter بشكل حقيقي (AOT/JIT كامل) يتطلّب Dart SDK + Gradle/Xcode
toolchain — أدوات build كاملة لا يمكن لتطبيق مثبَّت من المتجر تشغيلها على
نفسه، ولا تتوفر على الهاتف بدون بيئة تطوير كاملة، والمتاجر (Play/App Store)
تمنع تحميل/تنفيذ كود native ديناميكيًا داخل تطبيق منشور أصلًا.

**البديل المُنفَّذ هنا:** مُفسِّر (`Interpreter` في
`features/preview/logic/widget_interpreter.dart`) يبني **ودجتس Flutter
حقيقية** من كود المستخدم مباشرة، فتُرسَم بواسطة نفس محرك Flutter الذي يشغّل
IDE نفسه. النتيجة تفاعل حقيقي 100%: الأزرار تعمل فعليًا، `Navigator.push`
تنقّل حقيقي، `setState` يُعيد رسم الشاشة فعليًا — لكن ضمن حدود ما يفهمه
المُفسِّر من صياغة Dart (القسم التالي).

## 4) حدود المُفسِّر — ما هو مدعوم الآن بالضبط

**مدعوم:**
- شجرة ودجتس متشعبة كاملة عبر استدعاءات مُنشئات (`Scaffold(...)`, `Column(children: [...])`...)
- ثوابت Colors/Icons/FontWeight/MainAxisAlignment... الشائعة (راجع
  `builtin_widgets.dart` → `staticProperties` للقائمة الكاملة القابلة للتوسيع)
- أصناف `StatelessWidget` و`StatefulWidget`+`State` مُعرَّفة بصياغة قياسية:
  `class X extends StatelessWidget { Widget build(BuildContext context) { return ...; } }`
  و`class X extends StatefulWidget` مع `createState() => _XState();`
  و`class _XState extends State<X> { ... Widget build(...) {...} }`
- حقول حالة بسيطة (`int _counter = 0;`) تُحفظ فعليًا بين عمليات `setState`
- `setState(() { ... })` بجُمل: تعيين (`=`, `+=`, `-=`)، `++`/`--`، `if/else`، عوائد
- `Navigator.push(context, MaterialPageRoute(builder: (context) => Widget))`,
  `Navigator.pop`, `Navigator.pushNamed`, وخريطة `routes` في `MaterialApp`
- `widget.xxx` للوصول لحقول الودجت الأب من داخل صنف State
- String interpolation: `'العدد: $counter'` و`'${a + b}'`
- ternary، عمليات حسابية/منطقية/مقارنة أساسية، القوائم `[...]`

**غير مدعوم بعد (موثَّق عمدًا كحدود صريحة، وليس أخطاء):**
- حلقات `for`/`while`، دوال مساعدة إضافية خارج `build`، async/await
- استيراد وتنفيذ حزم pub خارجية داخل الكود المُفسَّر
- Widgets خارج القائمة المسجَّلة في `builtin_widgets.dart` (تظهر كعنصر نائب
  أحمر واضح "عنصر غير مدعوم بعد: X" بدل تعطّل المعاينة بالكامل)
- نسخ متعددة نشطة من نفس صنف Stateful في وقت واحد (الحالة تُخزَّن حاليًا
  بمفتاح اسم الصنف نفسه — كافٍ تمامًا للتنقل بين شاشات مختلفة، لكنه مبسَّط
  لحالة "قائمة من نفس الصنف تتكرر مع حالة مستقلة لكل عنصر")

عند أي خطأ تحليل أو تنفيذ، تظهر رسالة واضحة في لوحة المعاينة وفي الـ Console
بدل تعطّل التطبيق بالكامل — كل نقاط التنفيذ الحسّاسة (`_runBuild`,
`buildRoot`) مُغلَّفة بـ try/catch مع رسائل مفهومة.

## 5) ملاحظة أمانة تقنية مهمة حول هذا التسليم

هذا الكود **كُتب ونُظِّم يدويًا بعناية** لكنه **لم يُشغَّل ولم يُبنَ فعليًا**
في هذه المحادثة (لا يوجد اتصال إنترنت هنا لتنفيذ `flutter pub get` أو
`flutter run`). الأسماء والتوقيعات الدقيقة لبعض واجهات برمجة الحزم الخارجية
(خصوصًا `flutter_code_editor`: خصائص `CodeField`/`GutterStyle`/`LineNumberStyle`،
واسم الخاصية المستخدمة لقراءة النص الكامل من `CodeController`) اعتمدت على
معرفتي بهذه الحزمة وقد تحتاج **تعديلًا طفيفًا** لتطابق الإصدار الفعلي المثبَّت
عند أول `flutter pub get`. نفس الأمر لأسماء ثيمات `flutter_highlight`.

**الخطوة الأولى الموصى بها فعليًا:** نفّذ `flutter pub get` ثم `flutter analyze`،
وأصلح أي عدم تطابق في توقيعات هذه الحزمة الثلاث تحديدًا
(`flutter_code_editor`, `flutter_highlight`, `file_picker`) — بقية الكود
(المُفسِّر، نظام الملفات، الحالة) لا يعتمد على حزم خارجية غير مضمونة السلوك.

## 6) رحلة الاستخدام المُطبَّقة فعليًا

1. فتح التطبيق → شاشة ترحيب (3 صفحات) → "فتح مشروع من الجهاز"
2. اختيار مجلد → تظهر الشجرة في الشريط الجانبي (Explorer)
3. فتح `main.dart` من الشجرة → يُفتح في تبويب جديد بتلوين نحوي
4. تعديل الكود، حفظ (زر الحفظ في الشريط العلوي)
5. إنشاء ملف/مجلد جديد عبر قائمة "⋮" بجانب أي مجلد في الشجرة
6. الضغط على زر التشغيل (▶) في الشريط العلوي → يتحول المقطع تلقائيًا
   لعرض "المعاينة" (أو يدويًا عبر المفتاح بجانب اسم المشروع)
7. التفاعل الفعلي: ضغط أزرار، تنقّل بين شاشات، إدخال نص
8. العودة لتبويب "المحرر"، تعديل إضافي، حفظ، ثم "إعادة تشغيل" لرؤية التغييرات

---

## 7) البناء محليًا

```bash
flutter pub get
flutter run
```

يتطلّب صلاحية الوصول لمساحة التخزين على الجهاز (يطلبها `file_picker` تلقائيًا
عند أول استخدام لزر "فتح مجلد").
